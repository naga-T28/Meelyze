## 1. 概要 (Overview)

### 1.1 目的

本ドキュメントでは、`requirements.md` に定義された要件について、2026年8月25日時点のMVPで実装する範囲を明確にする。

MVPでは、開発メンバーが所有するiPhone上で、Meelyzeの主要ユーザーフローが一通り動作することを完成条件とする。

### 1.2 MVP対応区分

| MVP対応 | 意味 |
| --- | --- |
| 対応 | 2026年8月25日までに実装する |
| 一部対応 | 要件の一部をMVPとして実装する |
| 非対応 | 2026年8月25日時点では実装しない |

### 1.3 MVPの基本方針

- `Must` 要件は原則としてMVPで対応する
- `Should` / `Could` 要件は、コアユーザーフローに必要なものを除きMVP以降へ延期する
- `Won't` 要件はMVPでは実装しない
- App Store公開およびTestFlight配布はMVP対象外とする
- iOSは開発時点の最新正式版のみを対象とする
- 過去iOSバージョンへの対応は正式公開時に検討する
- 実装技術は `technology-selection.md` に従う
- アプリは安全性を保証せず、注文前に店員へ確認するための補助ツールとして実装する

## 2. MVPで採用する解析フロー

OCRで得られる結果は「認識文字列」であり、そのままローカルDBの料理名と一致するとは限らない。

例えば、以下のような入力が想定される。

```text
島豚の炙り沖縄そば 1,280円
特製ゴーヤーチャンプルー
県産和牛のにんにく醤油焼き
```

このため、OCRとDB照合の間に、料理名の抽出・意味解析・正規化を行う処理層を設ける。

### 2.1 MVP解析フロー

```text
メニュー画像
  ↓
Apple Vision OCR
  ↓
認識文字列
  ↓
前処理
  ├─ 空白・改行の整理
  ├─ 価格・記号等の除去
  └─ 明らかな不要文字列の除外
  ↓
Menu Understanding
  ├─ 料理項目の分割
  ├─ ベース料理名候補の抽出
  ├─ 明示食材の抽出
  ├─ 調理方法・修飾表現の分離
  └─ 未知語・未解決要素の抽出
  ↓
Normalization
  ├─ 全角・半角
  ├─ 空白
  ├─ ひらがな・カタカナ
  ├─ 長音
  ├─ OCR表記揺れ
  └─ 表記統一
  ↓
Alias Dictionary
  ├─ 別名
  ├─ 方言
  ├─ 商品名
  └─ 表記揺れ
  ↓
Canonical Entity
  ↓
SwiftData ローカルDB照合
```

### 2.2 LLMとルールベース処理の役割

MVPでは、**Local LLMとSwift / 正規表現の両方を採用する。**

どちらか一方に統一するのではなく、処理内容に応じて役割を分担する。

| 処理 | 採用手段 | MVP方針 |
| --- | --- | --- |
| 価格・通貨記号・メニュー番号の除去 | 正規表現 / Swiftロジック | 対応 |
| 空白・改行・記号等の整理 | Swiftロジック | 対応 |
| 全角半角・かな・長音等の表記統一 | Swift Normalization | 対応 |
| 既知の別名・方言・表記揺れの解決 | Alias Dictionary / SwiftData | 対応 |
| 料理項目の分割 | Local LLM + ルール | 対応 |
| ベース料理名の抽出 | Local LLM | 対応 |
| 明示食材の抽出 | Local LLM | 対応 |
| 調理方法・修飾表現の分離 | Local LLM | 対応 |
| 複合料理名・造語・文脈依存表現の解析 | Local LLM | 一部対応 |
| 最終的な料理DB照合 | SwiftData | 対応 |
| 最終的なアレルゲン判定 | Swift Rule Engine | 対応 |

基本方針は以下とする。

- **単純で決定論的に処理できる文字列処理はSwift / 正規表現で行う**
- **文脈理解が必要な料理名解析はLocal LLMで行う**
- LLMの出力をそのままDB照合には使用しない
- LLM出力は必ずNormalizationとAlias Dictionaryを通す
- 最終的なアレルゲン判定はLLMではなくDB + Rule Engineで行う

### 2.3 MVPで検討・検証する事項

採用技術自体は **Local LLM + Swift / 正規表現の併用** とし、MVP実装では両者の責務境界を検証する。

具体的には以下を確認する。

- 価格・通貨記号・メニュー番号などを正規表現で安定して除去できる範囲
- 料理名抽出のうち、ルールベースで十分処理できるパターン
- 文脈理解が必要となりLocal LLMへ渡すべきパターン
- LLM利用前に除去・正規化しておくべき情報
- LLM出力後にNormalizationで吸収すべき表記揺れ
- Alias Dictionaryへ登録すべき別名・方言・商品名
- DB照合できなかった場合に「未知料理」と判断する条件
- Local LLMが利用できない場合のフォールバック方法
- ルールベース処理とLLM処理の境界による処理時間・精度への影響

MVPでは、LLMと正規表現のどちらか一方を選定することを目的とせず、**それぞれが得意な処理を分担させた構成で主要な日本語メニューを安定してDB照合できること**を優先する。

## 3. 機能要件 (Functional Requirements)

### FR-1: 撮影・文字認識

| ID | 要件 | 優先度 | MVP対応 | 備考 |
| --- | --- | --- | --- | --- |
| FR-1.1 | 端末内OCRによりメニュー画像から文字列を抽出する | Must | 対応 | Apple Visionを使用する |
| FR-1.2 | OCRの認識言語ヒントを日本語に固定し、誤認識を抑制する | Must | 対応 | 日本語認識を優先する |
| FR-1.3 | 抽出文字列から価格・住所・店名等を除外し、料理名候補を抽出する | Must | 対応 | 正規表現・Swiftロジック・Local LLMを役割分担して利用する |
| FR-1.4 | 暗さ・ブレ・傾きを検出し、撮影前にガイドを表示する | Should | 一部対応 | MVPではOCR失敗時の再撮影案内と撮影のコツ表示までとする |
| FR-1.5 | ギャラリーから既存画像を選択して判定する | Could | 非対応 | MVP以降に対応する |
| FR-1.6 | 撮影画像を端末外へ送信しない | Must | 対応 | OCR・Local LLMとも端末内処理を基本とする |

### FR-2: 料理特定・アレルゲン判定

| ID | 要件 | 優先度 | MVP対応 | 備考 |
| --- | --- | --- | --- | --- |
| FR-2.1 | 料理名候補を正規化した上でローカルDBと照合する | Must | 対応 | Local LLM解析 → Normalization → Alias Dictionary → SwiftData照合の流れを採用する |
| FR-2.2 | DB照合成立時はDB情報から決定論的にアレルゲンを導出する | Must | 対応 | DB一致後の最終判定にはLLMを使用しない |
| FR-2.3 | 隠れ食材（だし・油脂・調味料）を判定対象に含める | Must | 対応 | Dish / Ingredient情報から判定する |
| FR-2.4 | DB照合が成立しない場合は未知・未解決要素として扱う | Must | 対応 | LLM推論のみで安全側の判定を行わない |
| FR-2.5 | DB照合できず十分な根拠がない場合は「判定不可」とする | Must | 対応 | 推測で「該当なし」としない |
| FR-2.6 | LLMによる含有可能性の推論は警告方向のEvidenceとして利用できる | Must | 対応 | Positiveな推論のみ補助根拠として利用する |
| FR-2.7 | 同一料理名に複数解釈がある場合は最も安全側の解釈を採用する | Must | 対応 | 解決不能なら「判定不可」とする |
| FR-2.8 | 判定結果を三値で表現し、二値化しない | Must | 対応 | 「含有の可能性が高い」「収録データ上は該当なし」「判定不可」 |

## 4. MVP主要ユーザーフロー

```text
初回起動
  ↓
免責事項への同意
  ↓
表示言語・アレルゲン・食事制限登録
  ↓
メニュー撮影
  ↓
Apple Vision OCR
  ↓
認識文字列
  ↓
正規表現 / Swift前処理
  ↓
Local LLMによるMenu Understanding
  ↓
Normalization
  ↓
Alias Dictionary
  ↓
SwiftDataローカルDB照合
  ↓
Risk Aggregation / Rule Engine
  │
  ├─ 十分な根拠あり
  │      ↓
  │   三値判定
  │
  └─ 未知・曖昧・解決不能
         ↓
      判定不可 / 要確認
  ↓
判定根拠表示
  ↓
店員向け確認カード
  ↓
必要に応じて翻訳支援
```

## 5. MVP技術構成

| 領域 | 採用技術 | MVPでの用途 |
| --- | --- | --- |
| 開発言語 | Swift | iOSアプリ全体 |
| UI | SwiftUI | 画面構築 |
| Architecture | MVVM + Repository / Service | 責務分離 |
| Camera | AVFoundation | メニュー撮影 |
| OCR | Apple Vision | 日本語文字認識 |
| Menu Understanding | Apple Foundation Models | メニューの意味解析・構造化 |
| LLM抽象化 | MenuUnderstandingService | LLM実装の差し替え |
| 前処理 | Swift / 正規表現 | 価格・記号等の除去 |
| Normalization | Swift独自ロジック | 表記統一 |
| Alias Dictionary | SwiftData | 同義語・方言・表記揺れ解決 |
| Local Database | SwiftData | 料理・食材・アレルゲン情報 |
| 初期データ | JSON | Git管理・初回インポート |
| 判定 | Swift Rule Engine | 決定論的な三値判定 |
| 翻訳 | Apple Translation Framework | 店員との翻訳支援 |
| Profile Storage | SwiftData | ユーザープロファイル保存 |
| Test | Swift Testing / XCTest | 判定・正規化・UIテスト |
