## 1. 概要 (Overview)

### 1.1 目的

本ドキュメントでは、`requirements.md` に定義された要件について、2026年8月25日時点のMVPで実装する範囲を明確にする。

MVPでは、開発メンバーが所有するiPhone上で、Meelyzeの主要ユーザーフローが一通り動作することを完成条件とする。

### 1.2 MVP対応区分

| MVP対応 | 意味                  |
| ----- | ------------------- |
| 対応    | 2026年8月25日までに実装する   |
| 一部対応  | 要件の一部をMVPとして実装する    |
| 非対応   | 2026年8月25日時点では実装しない |

### 1.3 MVPの基本方針

* `Must` 要件は原則としてMVPで対応する
* `Should` / `Could` 要件は、コアユーザーフローに必要なものを除きMVP以降へ延期する
* `Won't` 要件はMVPでは実装しない
* App Store公開およびTestFlight配布はMVP対象外とする
* iOSは開発時点の最新正式版のみを対象とする
* 過去iOSバージョンへの対応は正式公開時に検討する
* 実装技術は `technology-selection.md` に従う
* アプリは安全性を保証せず、注文前に店員へ確認するための補助ツールとして実装する

## 2. MVPで採用する解析フロー

OCRで得られる結果は「認識文字列」であり、そのままローカルDBの料理名と一致するとは限らない。

例えば、以下のような入力が想定される。

```text
島豚の炙り沖縄そば 1,280円
特製ゴーヤーチャンプルー
県産和牛のにんにく醤油焼き
```

このため、OCRとDB照合の間に、料理名の抽出・意味解析・正規化を行う処理層を設ける。

また、判定結果を撮影したメニュー画像上へ表示するため、OCR時に料理名だけでなく文字領域の位置情報（Bounding Box）も保持する。

### 2.1 MVP解析フロー

```text
メニュー画像
  ↓
Apple Vision OCR
  ↓
認識文字列 + Bounding Box
  ↓
前処理
  ├─ 空白・改行の整理
  ├─ 価格・記号等の除去
  └─ 明らかな不要文字列の除外
  ↓
Menu Understanding
  ├─ 料理項目の分割
  ├─ ベース料理名候補の抽出
  ├─ 明示食材の抽出
  ├─ 調理方法・修飾表現の分離
  └─ 未知語・未解決要素の抽出
  ↓
Normalization
  ├─ 全角・半角
  ├─ 空白
  ├─ ひらがな・カタカナ
  ├─ 長音
  ├─ OCR表記揺れ
  └─ 表記統一
  ↓
Alias Dictionary
  ├─ 別名
  ├─ 方言
  ├─ 商品名
  └─ 表記揺れ
  ↓
Canonical Entity
  ↓
SwiftData ローカルDB照合
  ↓
Risk Aggregation / Rule Engine
  ↓
判定結果 + Bounding Box
  ↓
メニュー画像上へ警告情報をオーバーレイ表示
```

### 2.2 LLMとルールベース処理の役割

MVPでは、**Local LLMとSwift / 正規表現の両方を採用する。**

どちらか一方に統一するのではなく、処理内容に応じて役割を分担する。

| 処理                 | 採用手段                         | MVP方針 |
| ------------------ | ---------------------------- | ----- |
| 価格・通貨記号・メニュー番号の除去  | 正規表現 / Swiftロジック             | 対応    |
| 空白・改行・記号等の整理       | Swiftロジック                    | 対応    |
| 全角半角・かな・長音等の表記統一   | Swift Normalization          | 対応    |
| 既知の別名・方言・表記揺れの解決   | Alias Dictionary / SwiftData | 対応    |
| 料理項目の分割            | Local LLM + ルール              | 対応    |
| ベース料理名の抽出          | Local LLM                    | 対応    |
| 明示食材の抽出            | Local LLM                    | 対応    |
| 調理方法・修飾表現の分離       | Local LLM                    | 対応    |
| 複合料理名・造語・文脈依存表現の解析 | Local LLM                    | 一部対応  |
| 最終的な料理DB照合         | SwiftData                    | 対応    |
| 最終的なアレルゲン判定        | Swift Rule Engine            | 対応    |

基本方針は以下とする。

* **単純で決定論的に処理できる文字列処理はSwift / 正規表現で行う**
* **文脈理解が必要な料理名解析はLocal LLMで行う**
* LLMの出力をそのままDB照合には使用しない
* LLM出力は必ずNormalizationとAlias Dictionaryを通す
* 最終的なアレルゲン判定はLLMではなくDB + Rule Engineで行う

### 2.3 MVPで検討・検証する事項

採用技術自体は **Local LLM + Swift / 正規表現の併用** とし、MVP実装では両者の責務境界を検証する。

具体的には以下を確認する。

* 価格・通貨記号・メニュー番号などを正規表現で安定して除去できる範囲
* 料理名抽出のうち、ルールベースで十分処理できるパターン
* 文脈理解が必要となりLocal LLMへ渡すべきパターン
* LLM利用前に除去・正規化しておくべき情報
* LLM出力後にNormalizationで吸収すべき表記揺れ
* Alias Dictionaryへ登録すべき別名・方言・商品名
* DB照合できなかった場合に「未知料理」と判断する条件
* Local LLMが利用できない場合のフォールバック方法
* ルールベース処理とLLM処理の境界による処理時間・精度への影響

MVPでは、LLMと正規表現のどちらか一方を選定することを目的とせず、**それぞれが得意な処理を分担させた構成で主要な日本語メニューを安定してDB照合できること**を優先する。

### 2.4 判定結果のメニュー画像へのオーバーレイ表示

MVPでは、判定した料理を別の料理一覧として表示するのではなく、**撮影したメニュー画像上に警告情報を重ねて表示する方式を採用する。**

利用者が実際のメニューと判定結果を行き来せず、そのままメニューを見ながら料理を確認し、店員への指差しにも利用できることを目的とする。

#### 表示フロー

```text
メニュー撮影
  ↓
Apple Vision OCR
  ↓
料理名・文字領域のBounding Boxを取得
  ↓
料理名抽出・正規化
  ↓
ローカルDB照合・アレルゲン判定
  ↓
判定結果と元画像上の料理位置を対応付け
  ↓
メニュー画像上に警告情報をオーバーレイ表示
```

#### オーバーレイ表示内容

料理ごとに、元画像上の該当位置へ以下の情報を表示する。

* アレルゲン警告
* 食事制限に該当する食材
* 「判定不可 / 要確認」
* DB判定またはLLM由来の補助情報の区別
* 詳細表示への導線

警告は色だけに依存せず、アイコン・テキストを併用する。

#### MVPでの方針

* Apple VisionからOCR結果とBounding Boxを取得する
* OCRで取得した料理名と画像上の位置情報をセットで保持する
* 解析・DB照合後も元の料理項目との対応関係を維持する
* 判定結果を該当する料理の位置へ重ねて表示する
* MVPでは料理一覧表示への置き換えを前提とせず、オーバーレイ表示まで実装する

### 2.5 料理DBのデータ作成方針

MVPでは、**Meelyze独自の料理DBを作成する。**

料理・食材・アレルゲン情報については、消費者庁等が公開する公的情報を随時参照しながら、Meelyzeの判定に必要な形式へ整理して独自DBとして管理する。

既存サービスや既存料理DBをそのまま複製して利用することは前提としない。

#### データ作成フロー

```text
公的情報・信頼できる情報源
  ↓
アレルゲン・食材情報を確認
  ↓
Meelyze用に料理データを整理
  ↓
JSONで初期データを管理
  ↓
アプリ初回起動時
  ↓
SwiftDataへインポート
```

#### MVPで管理する主なデータ

料理ごとに、少なくとも以下を管理する。

* 正規料理名
* 表記揺れ・別名
* 主な食材
* 隠れ食材

  * だし
  * 調味料
  * 油脂
  * ソース等
* 関連アレルゲン
* 食事制限に関係する食材
* 情報の根拠・参照元

#### MVPで実施すること

* 消費者庁等の公的情報を調査する
* アレルゲン情報の基準となる情報源を決定する
* 料理・食材情報として利用可能な公開情報を調査する
* 各情報源の利用条件・ライセンスを確認する
* MVPで収録する料理の対象範囲を決定する
* Meelyze独自の初期料理DBを作成する
* 料理ごとの情報源・根拠を追跡可能な形で管理する
* JSONからSwiftDataへ取り込める構造を作成する

MVPでは料理を網羅することよりも、**登録した料理について根拠のある食材・アレルゲン情報を保持すること**を優先する。

### FR-4: 翻訳・確認支援

Apple Translation Frameworkを利用する際、選択した言語によっては翻訳用言語データのダウンロードが必要となる。

ダウンロードのタイミングについて、以下の候補を比較した。

| タイミング       | メリット            | デメリット                |
| ----------- | --------------- | -------------------- |
| 言語選択時       | 店で使う時には準備済みにできる | 初回設定で突然DLが始まり重く感じる   |
| 初回翻訳時       | 必要になった人だけDLできる  | 店員との会話直前に待たされる可能性がある |
| 初回メニュー読み取り時 | 利用開始後なので自然      | OCRと関係のないDLが突然表示される  |

#### MVPでの採用方針

MVPでは、**初回の言語選択時に翻訳用言語データのダウンロードを案内する方式を採用する。**

飲食店で実際に翻訳機能が必要になったタイミングでダウンロード待ちが発生することを避けるため、アプリの初期設定段階で準備してもらうことを推奨する。

```text
初回起動
  ↓
表示言語を選択
  ↓
翻訳機能について説明
  ↓
翻訳用言語データのダウンロードを案内
  ↓
ユーザーがダウンロードを許可
  ↓
翻訳データを準備
  ↓
初期設定を継続
```

翻訳用言語データを利用できない場合でも、以下のコア機能は利用可能とする。

* OCR
* ローカルDB照合
* アレルゲン判定
* 店員向け定型確認カード

翻訳機能が利用できない場合は、定型確認カードをフォールバックとして利用する。

| ID     | 要件                                | 優先度              | MVP対応 | 備考                               |
| ------ | --------------------------------- | ---------------- | ----- | -------------------------------- |
| FR-4.1 | アレルゲンを差し込んだ日本語の確認カードを生成し、母語訳を併記する | Must             | 対応    | 店員へそのまま提示できる画面を作る                |
| FR-4.2 | 確認カードの定型文をアプリに同梱し、オフラインで生成できる     | Must             | 対応    | 通信なしでも利用可能にする                    |
| FR-4.3 | 日本語⇔母語の双方向自由入力翻訳を提供する             | Must             | 対応    | Apple Translation Frameworkを利用する |
| FR-4.4 | 翻訳ではアレルゲン可否・推奨・安全性の見解を生成しない       | Must             | 対応    | 翻訳用途のみに制限する                      |
| FR-4.5 | 翻訳利用不可時は定型フレーズ集を提示する              | Must             | 対応    | 確認カードをフォールバックとして利用する             |
| FR-4.6 | 初回の言語選択時に翻訳用言語データのダウンロードを案内する     | Must             | 対応    | 店舗利用前に翻訳環境を準備する                  |
| FR-4.7 | 確認カードおよび翻訳結果の読み上げを提供する            | Won't (Post-MVP) | 非対応   | MVP以降の対象とする                      |

## 4. MVP主要ユーザーフロー

```text
初回起動
  ↓
免責事項への同意
  ↓
表示言語を選択
  ↓
翻訳用言語データのダウンロードを案内
  ↓
アレルゲン・食事制限登録
  ↓
メニュー撮影
  ↓
Apple Vision OCR
  ↓
認識文字列 + Bounding Box
  ↓
正規表現 / Swift前処理
  ↓
Local LLMによるMenu Understanding
  ↓
Normalization
  ↓
Alias Dictionary
  ↓
SwiftDataローカルDB照合
  ↓
Risk Aggregation / Rule Engine
  │
  ├─ 十分な根拠あり
  │      ↓
  │   三値判定
  │
  └─ 未知・曖昧・解決不能
         ↓
      判定不可 / 要確認
  ↓

  ↓

  ↓
店員向け確認カード
  ↓
必要に応じて翻訳支援
```

## 5. MVP技術構成

| 領域                 | 採用技術                        | MVPでの用途                |
| ------------------ | --------------------------- | ---------------------- |
| 開発言語               | Swift                       | iOSアプリ全体               |
| UI                 | SwiftUI                     | 画面構築・警告オーバーレイ          |
| Architecture       | MVVM + Repository / Service | 責務分離                   |
| Camera             | AVFoundation                | メニュー撮影                 |
