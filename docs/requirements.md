## 1. 概要 (Overview)

### 1.1 目的

食物アレルギーや宗教・信条上の食事制限を持つ訪日旅行者が、日本語で記載された飲食店のメニューをカメラで撮影するだけで、各料理に含まれる可能性のあるアレルゲン・制限食材を母語で把握できるようにする。

判定結果は撮影したメニュー画像上の該当料理位置に重ねて表示し、利用者が実際のメニューを見ながら確認できるようにする。あわせて、店員へ確認するための翻訳支援機能を提供し、「注文前の確認」という最終的な安全確保の行動を後押しする。

### 1.2 背景

食事制限を持つ旅行者は、現地語のメニューから料理を選ぶ際、料理名や食材を一つひとつ調べたり、含まれる食材を推測したうえで注文したりする必要があり、大きな負担となっている。

特に沖縄料理は地域独自性が高く、料理名から食材や調理方法を判断することが難しい。「ラフテー」「ソーキ」「ミミガー」「テビチ」はいずれも豚肉料理だが名称からは判別できず、ラード・豚骨だし・かつおだしは料理名に一切現れない**隠れ食材**として広範に使われる。これはアレルギーだけでなく、ハラール（豚・アルコール）やベジタリアン（動物性だし）の観点でも重大な問題となる。

沖縄は訪日旅行者の主要な受け入れ地域であり、この課題の解消は現地の飲食体験の質に直結する。

### 1.3 成功の定義

本プロダクトは**「注文前に店員へ確認するための補助ツール」**であり、安全を保証するものではない。この位置づけを前提に、成功指標を以下のとおり定義する。

| ID | 指標 | 目標値 |
| --- | --- | --- |
| KPI-1 | **偽陰性率**（実際は含まれるのに「含まれない」と表示した件数の割合） | **0%（最優先。他のすべての指標に優先する）** |
| KPI-2 | 未知の料理を正しく「判定不可」と表示できる率 | 95%以上 |
| KPI-3 | 収録済み料理の撮影から判定表示までの時間（オフライン時） | 3秒以内 |
| KPI-4 | 収録済み料理のカバレッジ（沖縄県内主要店舗のメニュー実サンプルに対する照合率） | 80%以上 |
| KPI-5 | 判定表示から店員向け確認カード提示までの操作数 | 3タップ以内 |

> **設計原則**: 精度とは「当てること」ではなく「**誤って安全と言わないこと**」と定義する。曖昧な場合は必ず「不明」に倒す。

## 2. 用語定義 (Glossary)

| 用語 | 定義 |
| --- | --- |
| 特定原材料 | 食品表示法で表示が義務付けられた品目 |
| 特定原材料に準ずるもの | 食品表示において表示が推奨される品目 |
| 食事制限 (Dietary Restriction) | アレルゲン以外の摂取回避対象。ハラール、ベジタリアン、ヴィーガン、ノンアルコール等 |
| 隠れ食材 | 料理名からは判別できないが調理過程で使用される食材（ラード、かつおだし、豚骨だし、みりん等） |
| 収録済み料理 | 人手でキュレーションされローカルDBに格納された料理。DB情報から決定論的に判定可能 |
| 未知料理 | 正規化・Alias Dictionary適用後もローカルDBに照合できない、または解釈を一意に確定できない料理 |
| Local LLM | 端末内で動作し、料理項目の分割・料理名候補・明示食材・修飾表現等の構造化に利用する生成モデル |
| Bounding Box | OCRで検出した文字領域の画像上の位置情報。判定結果を元のメニュー画像上へ重ねて表示するために利用する |
| 判定三値 | 「含有の可能性が高い」/「収録データ上は該当なし」/「判定不可」の3状態 |
| 偽陰性 (False Negative) | 実際は含まれるアレルゲンを「該当なし」と表示すること。本プロダクトにおける最重大の障害 |
| 確認カード | 店員に見せるための日本語の確認文面。ユーザーの母語訳を併記する |
| 要配慮個人情報 | 個人情報保護法上、取得に本人同意を要する情報。病歴に準じるアレルギー情報を含み得る |
| EARS | Easy Approach to Requirements Syntax。本書の機能要件の記述形式 |

## 3. ユーザーストーリー (User Stories)

### US-1: メニュー撮影によるアレルゲン推定

**ストーリー**: 食物アレルギーを持つ訪日旅行者として、料理を選ぶたびに店員へ質問する負担を減らすために、メニューを撮影して各料理のアレルゲン情報を母語で確認できる。

**受け入れ基準 (Acceptance Criteria)**:

- [ ] AC-1.1: WHEN ユーザーがメニューを撮影する THEN システムは画像内の料理名とBounding Boxを抽出し、料理ごとに判定三値のいずれかを元のメニュー画像上へ重ねて表示すること
- [ ] AC-1.2: WHEN 登録済みアレルゲンが含まれる可能性がある料理を検出した THEN システムは元画像上の当該料理位置に警告を明示し、該当アレルゲン名を母語で表示すること
- [ ] AC-1.3: WHEN 料理がローカルDBに存在せず十分な根拠を得られない THEN システムは「判定不可」と表示し、安全側の推測を行わないこと
- [ ] AC-1.4: WHEN OCRが文字を1件も抽出できなかった THEN システムは再撮影を促し、撮影のコツ（明るさ・角度・接写）を提示すること
- [ ] AC-1.5: システムはいかなる場合も「安全です」「食べられます」と断定する文言を表示しないこと

### US-2: 店員への確認支援（確認カード）

**ストーリー**: 日本語を話せない旅行者として、最終確認を店員に取るために、自分のアレルギー内容を日本語で正確に伝える文面を提示できる。

**受け入れ基準**:

- [ ] AC-2.1: WHEN ユーザーが料理の詳細表示から確認カードを要求した THEN システムは登録済みアレルゲンを差し込んだ日本語の定型文と、その母語訳を同一画面に併記表示すること
- [ ] AC-2.2: WHILE 確認カードを表示している間、システムは画面輝度を上げ、スリープを抑止すること
- [ ] AC-2.3: システムは確認カードをオフラインで表示できること
- [ ] AC-2.4: WHEN 判定結果が「収録データ上は該当なし」であった THEN システムは確認カードへの導線を非表示にせず、常に提示すること

### US-3: 自由入力による翻訳支援

**ストーリー**: 定型文では伝えきれない事情を持つ旅行者として、店員と細かいやり取りをするために、自由に入力した文章を日本語へ翻訳し、店員の返答を母語へ翻訳し返すことができる。

**受け入れ基準**:

- [ ] AC-3.1: WHEN ユーザーが母語で文章を入力した THEN システムはApple Translation Frameworkを用いて日本語訳を表示すること
- [ ] AC-3.2: WHEN ユーザーが日本語（店員の返答）を入力した THEN システムは母語訳を表示すること
- [ ] AC-3.3: システムは翻訳以外の応答、特にアレルゲンの可否に関する見解を生成しないこと
- [ ] AC-3.4: WHEN ユーザーが初回の表示言語を選択した THEN システムは翻訳用言語データのダウンロードを案内すること
- [ ] AC-3.5: IF 必要な翻訳用言語データを利用できない THEN システムは自由入力翻訳を利用不可として示し、定型確認カードまたは定型フレーズへの導線を表示すること

### US-4: アレルギープロファイルの登録

**ストーリー**: 利用者として、毎回条件を入力し直す手間を避けるために、自分のアレルゲンと食事制限を一度登録して保持できる。

**受け入れ基準**:

- [ ] AC-4.1: WHEN 初回起動時 THEN システムは対象アレルゲン品目および食事制限区分の一覧から複数選択できる登録画面を表示すること
- [ ] AC-4.2: システムは登録内容を端末内にのみ保存し、外部サーバーへ送信しないこと
- [ ] AC-4.3: WHEN ユーザーが複数人分のプロファイルを作成した THEN システムは判定時にプロファイルを切り替えられること（同行者対応）

### US-5: オフライン利用

**ストーリー**: 通信環境が不安定な旅行者として、電波の届かない店舗や離島でも、定番料理については判定を得られる。

**受け入れ基準**:

- [ ] AC-5.1: WHILE 機内モードまたは圏外の間、システムはOCR・ローカルDB照合・判定表示・確認カードの各コア機能を提供すること
- [ ] AC-5.2: WHILE 必要な翻訳用言語データが端末に準備済みである間、システムはApple Translation Frameworkによる翻訳支援を利用可能とすること
- [ ] AC-5.3: WHEN 未知料理を検出し十分な根拠を得られない THEN システムは「判定不可」と表示すること

### US-6: 宗教・信条上の食事制限への対応

**ストーリー**: ハラールまたはベジタリアンを実践する旅行者として、料理名に現れない食材を避けるために、豚由来成分・アルコール・動物性だしの含有可能性を確認できる。

**受け入れ基準**:

- [ ] AC-6.1: WHEN ハラールを選択したユーザーが判定を実行した THEN システムは豚肉・豚由来成分（ラード、豚骨だし、ゼラチン）・アルコール（みりん、料理酒）の含有可能性を個別に表示すること
- [ ] AC-6.2: WHEN ベジタリアン/ヴィーガンを選択したユーザーが判定を実行した THEN システムは動物性だし（かつおだし、煮干し、豚骨）を含有可能性として表示すること
- [ ] AC-6.3: システムは宗教上の適合性を認証・保証する表現を用いず、あくまで含有可能性の提示に留めること

## 4. 機能要件 (Functional Requirements)

### FR-1: 撮影・文字認識

| ID | 要件 | 優先度 | 関連US |
| --- | --- | --- | --- |
| FR-1.1 | WHEN ユーザーが撮影を実行した THEN システムは端末内OCRによりメニュー画像から文字列を抽出すること | Must | US-1 |
| FR-1.2 | システムはOCRの認識言語ヒントを日本語に固定し、誤認識を抑制すること | Must | US-1 |
| FR-1.3 | システムは抽出した文字列から、価格・住所・店名等を除外し料理名候補を抽出すること | Must | US-1 |
| FR-1.4 | IF 画像が暗い・ブレている・傾いている場合 THEN システムは撮影前またはOCR失敗時に撮影ガイドを表示し再撮影を促すこと | Should | US-1 |
| FR-1.5 | システムは端末のギャラリーから既存画像を選択して判定できること | Could | US-1 |
| FR-1.6 | システムは撮影画像を端末外へ送信しないこと | Must | US-1 |
| FR-1.7 | システムはOCRで認識した料理名候補とBounding Boxを対応付けて保持し、解析・判定後まで対応関係を維持すること | Must | US-1 |

### FR-2: 料理特定・アレルゲン判定

| ID | 要件 | 優先度 | 関連US |
| --- | --- | --- | --- |
| FR-2.1 | システムは料理名候補を正規化（全角半角・送り仮名・カタカナ表記ゆれ・異体字等）したうえでAlias Dictionaryを適用し、ローカルDBと照合すること | Must | US-1 |
| FR-2.2 | WHEN 照合が成立した THEN システムはDBの食材情報からアレルゲンを決定論的に導出し、LLMを最終判定に用いないこと | Must | US-1 |
| FR-2.3 | システムは料理に紐づく隠れ食材（だし・油脂・調味料）を判定対象に必ず含めること | Must | US-1, US-6 |
| FR-2.4 | IF DB照合が成立しない THEN システムは当該料理を未知・未解決要素として扱うこと | Must | US-1, US-5 |
| FR-2.5 | IF DB照合できず十分な根拠がない THEN システムは「判定不可」を表示し、推測によって「該当なし」と判定しないこと | Must | US-1, US-5 |
| FR-2.6 | システムはLocal LLMによる含有可能性の推論を警告方向の補助Evidenceとして利用できるが、LLMが食材を挙げなかったことを「含まれない」根拠として利用しないこと | Must | US-1 |
| FR-2.7 | システムは同一料理名に複数の解釈が存在する場合、最も安全側の解釈を採用し、解決不能な場合は「判定不可」とすること | Must | US-1 |
| FR-2.8 | システムは判定結果を「含有の可能性が高い」「収録データ上は該当なし」「判定不可」の三値で表現し、二値化しないこと | Must | US-1 |

### FR-4: 翻訳・確認支援

翻訳用言語データの準備タイミングについて、以下を比較する。

| タイミング | メリット | デメリット |
| --- | --- | --- |
| 言語選択時 | 店で使う時には準備済みにできる | 初回設定でDLが発生し、重く感じる可能性がある |
| 初回翻訳時 | 翻訳を使う人だけDLできる | 店員との会話直前に待ち時間が発生する可能性がある |
| 初回メニュー読み取り時 | アプリ利用開始後なので比較的自然 | OCRとは直接関係のないDLが読み取り時に発生する |

MVPでは、**言語選択時に翻訳用言語データのダウンロードを案内する方式を採用する。**

旅行先の店舗で翻訳が必要になった時点でダウンロード待ちが発生することを避け、利用前に準備できることを優先する。ダウンロードできなかった場合でも、OCR・DB判定・定型確認カードは利用可能とする。

| ID | 要件 | 優先度 | 関連US |
| --- | --- | --- | --- |
| FR-4.1 | システムはユーザーのアレルゲンを差し込んだ日本語の確認カードを生成し、母語訳を併記すること | Must | US-2 |
| FR-4.2 | システムは確認カードの定型文をアプリに同梱し、オフラインで生成できること | Must | US-2, US-5 |
| FR-4.3 | WHEN ユーザーが自由入力した THEN システムはApple Translation Frameworkを用いて日本語⇔母語の双方向翻訳を提供すること | Must | US-3 |
| FR-4.4 | システムは翻訳において、アレルゲンの可否判断・推奨・安全性の見解を生成しないこと | Must | US-3 |
| FR-4.5 | IF 必要な翻訳用言語データを利用できない THEN システムは定型フレーズ集または確認カードを代替提示すること | Must | US-3, US-5 |
| FR-4.6 | WHEN ユーザーが初回の表示言語を選択した THEN システムは必要な翻訳用言語データのダウンロードを案内すること | Must | US-3, US-4 |
| FR-4.7 | システムは確認カードおよび翻訳結果の読み上げを提供すること | Won't (Post-MVP) | US-2 |

### FR-6: オフライン動作とデータ更新

Meelyzeでは、消費者庁等の公的情報を随時参照しながら、料理・食材・アレルゲン情報を整理した**独自料理DB**を作成する。

| ID | 要件 | 優先度 | 関連US |
| --- | --- | --- | --- |
| FR-6.1 | システムはMeelyze独自の料理DBをアプリに同梱し、初回起動時から通信なしで利用可能とすること | Must | US-5 |
| FR-6.2 | システムは料理DBの各データについて、情報の根拠・参照元を追跡可能な形で管理すること | Must | US-1, US-5 |
| FR-6.3 | WHEN 料理・食材・アレルゲン情報を作成または更新する THEN 消費者庁等の公的情報および信頼できる情報源を確認し、利用条件・ライセンスに従うこと | Must | US-1 |
| FR-6.4 | WHEN オンラインかつDB更新が存在する THEN システムは差分更新を取得すること | Should | US-5 |
| FR-6.5 | システムは過去の判定結果を端末内に履歴として保存し、オフラインで参照できること | Should | US-5 |
| FR-6.6 | WHEN 未知料理を検出した THEN システムは「判定不可」として扱い、推測によって安全側の結果を生成しないこと | Must | US-5 |

## 5. 非機能要件 (Non-Functional Requirements)

### 5.1 パフォーマンス

- **NFR-1.1**: 収録済み料理の判定は、撮影完了から結果表示まで3秒以内（オフライン、対象端末基準）
- **NFR-1.2**: OCR処理は1画像あたり1.5秒以内を目標とする
- **NFR-1.3**: Local LLMを伴うMenu Understanding処理が所定時間を超過した場合、ルールベース処理へフォールバックし、解決できない料理は「判定不可」とする
- **NFR-1.4**: アプリサイズは同梱するモデル・料理DB・翻訳関連データによる影響を確認し、MVP実機で利用可能な範囲に収める

### 5.2 セキュリティ・プライバシー

- **NFR-2.1**: アレルギー情報は要配慮個人情報に該当し得るため、端末内にのみ保存し、サーバーへ送信・保存しない
- **NFR-2.2**: アカウント登録を要求しない。個人を識別する情報を取得しない
- **NFR-2.3**: OCR・Menu Understanding・料理DB照合・アレルゲン判定は原則として端末内で完結させ、撮影画像を外部へ送信しない
- **NFR-2.4**: ユーザープロファイルはSwiftData等の端末内ストレージで管理し、外部サーバーと同期しない

### 5.3 可用性・信頼性

- **NFR-3.1**: コア機能（OCR・DB照合・判定・確認カード）はサーバー稼働状況に依存せず動作すること
- **NFR-3.2**: IF Local LLMが利用できない、または処理に失敗した場合 THEN システムはルールベース処理とローカルDB照合を維持し、解決できない料理のみ「判定不可」として縮退動作すること
- **NFR-3.3**: 判定ロジックまたは料理DBの変更時は、既知の偽陰性ケースを含む回帰テストセットを全件通過すること
- **NFR-3.4**: 翻訳用言語データを利用できない場合でも、OCR・DB照合・判定・確認カードのコア機能は継続利用できること

### 5.4 ユーザビリティ・アクセシビリティ

- **NFR-4.1**: 主要導線（起動→撮影→判定→確認カード）を5タップ以内で完結させること
- **NFR-4.2**: 警告表示は色覚多様性に配慮し、色・アイコン・テキストの3要素で冗長化すること
- **NFR-4.3**: OSのフォントサイズ設定（最大設定時）でレイアウトが破綻しないこと
- **NFR-4.4**: 屋外・薄暗い店内の双方で判読可能なコントラスト比（WCAG AA相当）を確保すること
- **NFR-4.5**: 免責・注意文は初回起動時に明示的な同意を取得し、以降も判定画面上に常時表示すること
- **NFR-4.6**: 判定結果は撮影したメニュー画像との位置関係を維持し、利用者が実際の料理名を指し示しながら確認できること

### 5.5 保守性・拡張性

- **NFR-5.1**: 料理データは `dish_id + 多言語ラベル配列 + 食材ID配列` の正規化構造とし、特定言語に依存しないこと
- **NFR-5.2**: 食材とアレルゲンの対応は、料理データと独立したマスタとして管理し、アレルゲン基準の変更・追加をデータ変更中心で吸収できること
- **NFR-5.3**: 表示言語の追加が、翻訳リソースおよび必要な言語設定の追加を中心として対応できること
- **NFR-5.4**: Local LLMによるMenu Understanding部分を `MenuUnderstandingService` 等のインターフェースで抽象化し、実装変更を他ロジックへ波及させないこと
- **NFR-5.5**: 料理データはコードから分離し、JSON等の非コード形式でソース管理すること
- **NFR-5.6**: 料理データには情報の根拠・参照元を保持し、後から出典を確認・更新できること

## 6. 制約条件 (Constraints)

### 6.1 プロダクトの位置づけ（最重要）

- **C-1**: 本プロダクトは**注文前に店員へ確認するための補助ツール**であり、摂食の安全を保証しない。医療機器ではなく、医学的助言を提供しない
- **C-2**: 判定は「含まれない」ことの証明を行わない。表示は常に「含有の可能性」または「収録データ上は該当なし」という限定的表現に留める
- **C-3**: 免責事項への同意を初回起動の必須要件とし、正式公開時にはアプリストア掲載文にも位置づけを明記する

### 6.2 技術

- **C-4**: MVPはiOSネイティブアプリとしてSwift / SwiftUIを採用し、開発時点の最新正式版iOSを対象とする
- **C-5**: OCRはApple Visionを用いて端末内で完結させ、認識文字列とBounding Boxを取得する
- **C-6**: Local LLMはApple Foundation Modelsを第一候補とし、料理項目の分割・料理名候補・明示食材・調理方法・修飾表現等のMenu Understandingに利用する
- **C-7**: 単純で決定論的な前処理・NormalizationはSwift / 正規表現で行う
- **C-8**: 最終的な料理照合はSwiftData上のローカルDB、最終的なアレルゲン判定はSwift Rule Engineで行う。LLM単独で「該当なし」を確定しない
- **C-9**: ローカルDBはSwiftDataを使用し、初期料理データはJSONとしてアプリに同梱する
- **C-10**: アプリ構成はMVVM + Repository / Serviceを採用する
- **C-11**: 翻訳支援はApple Translation Frameworkを利用する

### 6.3 事業・運営

- **C-12**: ユーザーに対して完全無料で提供する。収益化・広告を行わない
- **C-13**: MVPでは外部AI APIを前提とせず、主要処理を端末内で完結させる
- **C-14**: 少人数開発のため、24時間の障害対応・問い合わせ対応は行わない

### 6.4 法令・データ

- **C-15**: 個人情報保護法における要配慮個人情報の取扱いに配慮し、本設計では端末内保存によりサーバー側の取得を回避する
- **C-16**: 料理データの構築において、他社サービスのデータベースを無断で複製しない
- **C-17**: 料理・食材・アレルゲン情報は、消費者庁等の公的情報および信頼できる情報源を随時参照し、利用条件・ライセンスを確認したうえでMeelyze独自DBとして整理する
- **C-18**: ハラール等の宗教的適合性について、認証機関に代わる保証・認定を行わない

## 7. スコープ外 (Out of Scope)

| 項目 | 理由 / 将来対応 |
| --- | --- |
| 日本人が海外で使う逆方向の利用 | データモデルは対応可能な構造とするが、料理データ整備はPost-MVPで段階的に検討する |

| 過去iOSバージョンへの互換対応 | 正式公開時に検討する |

## 8. 前提条件・依存関係 (Assumptions & Dependencies)

### 前提条件

- **A-1**: ユーザーは自身のアレルゲンを正確に把握しており、初回起動時に登録する
- **A-2**: ユーザーは判定結果を最終判断とせず、店員への確認を行う（免責同意で明示）
- **A-3**: メニューは印刷物であり、撮影可能な明るさと角度を確保できる
- **A-4**: 店舗側に確認を求めた際、店員が一定の回答を返せる（店舗の協力を強制はできない）

### 依存関係

- **D-1**: Apple Visionの日本語OCR精度およびBounding Box取得精度
- **D-2**: Apple Foundation Modelsの対応端末・利用可能条件、およびMenu Understandingに必要な精度
- **D-3**: キュレーション済み料理データの整備。これがプロダクト品質の中核であり、開発工数の大きな割合を占める
- **D-4**: Apple Translation Frameworkの対象言語対応、および端末への翻訳用言語データの準備状況
- **D-5**: 消費者庁等の公的情報・信頼できる情報源から料理DB作成に必要な根拠情報を継続的に確認できること

## 付録A: データモデル方針（design.md への申し送り）

将来の多言語・対象地域拡張を成立させるため、以下の分離を初期から徹底する。この構造を後から変更するのが最も高コストな手戻りとなる。

```text
dishes
  : dish_id, region, representative_image, source_id

dish_labels
  : dish_id, lang(ja/en/zh-Hant/zh-Hans/ko), name, aliases

dish_ingredients
  : dish_id, ingredient_id, confidence(確実/一般的/店舗による), hidden_ingredient_flag

ingredients
  : ingredient_id, multilingual_name

ingredient_tags
  : ingredient_id, tag_id

tags
  : tag_id, type(allergen / halal / vegetarian / vegan), multilingual_name

sources
  : source_id, source_name, source_url_or_reference, checked_at, notes
