## 1. 概要(Overview)

### 1.1 目的

食物アレルギーや宗教・信条上の食事制限を持つ訪日旅行者が、日本語で記載された飲食店のメニューをカメラで撮影するだけで、各料理に含まれる可能性のあるアレルゲン・制限食材を母語で把握できるようにする。あわせて、店員へ確認するための翻訳支援機能を提供し、「注文前の確認」という最終的な安全確保の行動を後押しする。

### 1.2 背景

食事制限を持つ旅行者は、現地語のメニューから料理を選ぶ際、料理名や食材を一つひとつ調べたり、含まれる食材を推測したうえで注文したりする必要があり、大きな負担となっている。

特に沖縄料理は地域独自性が高く、料理名から食材や調理方法を判断することが難しい。「ラフテー」「ソーキ」「ミミガー」「テビチ」はいずれも豚肉料理だが名称からは判別できず、ラード・豚骨だし・かつおだしは料理名に一切現れない**隠れ食材**として広範に使われる。これはアレルギーだけでなく、ハラール(豚・アルコール)やベジタリアン(動物性だし)の観点でも重大な問題となる。

沖縄は訪日旅行者の主要な受け入れ地域であり、この課題の解消は現地の飲食体験の質に直結する。

### 1.3 成功の定義

本プロダクトは**「注文前に店員へ確認するための補助ツール」**であり、安全を保証するものではない。この位置づけを前提に、成功指標を以下のとおり定義する。

| ID | 指標 | 目標値 |
|----|------|--------|
| KPI-1 | **偽陰性率**(実際は含まれるのに「含まれない」と表示した件数の割合) | **0%(最優先。他のすべての指標に優先する)** |
| KPI-2 | 未知の料理を正しく「判定不可」と表示できる率 | 95%以上 |
| KPI-3 | 収録済み料理の撮影から判定表示までの時間(オフライン時) | 3秒以内 |
| KPI-4 | 収録済み料理のカバレッジ(沖縄県内主要店舗のメニュー実サンプルに対する照合率) | 80%以上 |
| KPI-5 | 判定表示から店員向け確認カード提示までの操作数 | 3タップ以内 |
| KPI-6 | AI推論API呼び出し率(全判定に占める未知料理の割合) | 20%以下(無料運営の維持条件) |

> **設計原則**: 精度とは「当てること」ではなく「**誤って安全と言わないこと**」と定義する。曖昧な場合は必ず「不明」に倒す。

## 2. 用語定義(Glossary)

| 用語 | 定義 |
|------|------|
| 特定原材料 | 食品表示法で表示が義務付けられた8品目(えび、かに、くるみ、小麦、そば、卵、乳、落花生) |
| 特定原材料に準ずるもの | 表示が推奨される20品目(アーモンド、いか、いくら、オレンジ、カシューナッツ、キウイ、牛肉、ごま、さけ、さば、大豆、鶏肉、バナナ、豚肉、まつたけ、もも、やまいも、りんご、ゼラチン、あわび) |
| 食事制限(Dietary Restriction) | アレルゲン以外の摂取回避対象。ハラール、ベジタリアン、ヴィーガン、ノンアルコール等 |
| 隠れ食材 | 料理名からは判別できないが調理過程で使用される食材(ラード、かつおだし、豚骨だし、みりん等) |
| 収録済み料理 | 人手でキュレーションされローカルDBに格納された料理。決定論的に判定可能 |
| 未知料理 | ローカルDBに照合しない料理。オンライン時のみAI推論の対象となる |
| 判定三値 | 「含有の可能性が高い」/「収録データ上は該当なし」/「判定不可」の3状態 |
| 偽陰性(False Negative) | 実際は含まれるアレルゲンを「該当なし」と表示すること。本プロダクトにおける最重大の障害 |
| 確認カード | 店員に見せるための日本語の確認文面。ユーザーの母語訳を併記する |
| 要配慮個人情報 | 個人情報保護法上、取得に本人同意を要する情報。病歴に準じるアレルギー情報を含み得る |
| EARS | Easy Approach to Requirements Syntax。本書の機能要件の記述形式 |

## 3. ユーザーストーリー(User Stories)

### US-1: メニュー撮影によるアレルゲン推定

**ストーリー**: 食物アレルギーを持つ訪日旅行者として、料理を選ぶたびに店員へ質問する負担を減らすために、メニューを撮影して各料理のアレルゲン情報を母語で確認できる。

**受け入れ基準(Acceptance Criteria)**:
- [ ] AC-1.1: WHEN ユーザーがメニューを撮影する THEN システムは画像内の料理名を抽出し、料理ごとに判定三値のいずれかを表示すること
- [ ] AC-1.2: WHEN 登録済みアレルゲンが含まれる可能性がある料理を検出した THEN システムは当該料理を警告色で明示し、該当アレルゲン名を母語で表示すること
- [ ] AC-1.3: WHEN 料理がローカルDBに存在せずオフラインである THEN システムは「判定不可」と表示し、推測による判定結果を表示しないこと
- [ ] AC-1.4: WHEN OCRが文字を1件も抽出できなかった THEN システムは再撮影を促し、撮影のコツ(明るさ・角度・接写)を提示すること
- [ ] AC-1.5: システムはいかなる場合も「安全です」「食べられます」と断定する文言を表示しないこと

### US-2: 店員への確認支援(確認カード)

**ストーリー**: 日本語を話せない旅行者として、最終確認を店員に取るために、自分のアレルギー内容を日本語で正確に伝える文面を提示できる。

**受け入れ基準**:
- [ ] AC-2.1: WHEN ユーザーが料理の詳細画面で確認カードを要求した THEN システムは登録済みアレルゲンを差し込んだ日本語の定型文と、その母語訳を同一画面に併記表示すること
- [ ] AC-2.2: WHILE 確認カードを表示している間、システムは画面輝度を上げ、スリープを抑止すること
- [ ] AC-2.3: システムは確認カードをオフラインで表示できること
- [ ] AC-2.4: WHEN 判定結果が「該当なし」であった THEN システムは確認カードへの導線を非表示にせず、常に提示すること

### US-3: 自由入力による翻訳チャット

**ストーリー**: 定型文では伝えきれない事情を持つ旅行者として、店員と細かいやり取りをするために、自由に入力した文章を日本語へ翻訳し、店員の返答を母語へ翻訳し返すことができる。

**受け入れ基準**:
- [ ] AC-3.1: WHEN ユーザーが母語で文章を入力した THEN システムは日本語訳を表示すること
- [ ] AC-3.2: WHEN ユーザーが日本語(店員の返答)を入力した THEN システムは母語訳を表示すること
- [ ] AC-3.3: システムは翻訳以外の応答、特にアレルゲンの可否に関する見解を生成しないこと
- [ ] AC-3.4: IF オフラインである THEN システムはチャット機能を無効化し、定型フレーズ集への導線を表示すること

### US-4: アレルギープロファイルの登録

**ストーリー**: 利用者として、毎回条件を入力し直す手間を避けるために、自分のアレルゲンと食事制限を一度登録して保持できる。

**受け入れ基準**:
- [ ] AC-4.1: WHEN 初回起動時 THEN システムは28品目および食事制限区分の一覧から複数選択できる登録画面を表示すること
- [ ] AC-4.2: システムは登録内容を端末内にのみ保存し、外部サーバーへ送信しないこと
- [ ] AC-4.3: WHEN ユーザーが複数人分のプロファイルを作成した THEN システムは判定時にプロファイルを切り替えられること(同行者対応)

### US-5: オフライン利用

**ストーリー**: 通信環境が不安定な旅行者として、電波の届かない店舗や離島でも、定番料理については判定を得られる。

**受け入れ基準**:
- [ ] AC-5.1: WHILE 機内モードまたは圏外の間、システムはOCR・DB照合・判定表示・確認カードの各機能を提供すること
- [ ] AC-5.2: WHEN オフラインで未知料理を検出した THEN システムは当該料理を「オンライン時に再判定可能」として記録し、通信回復時に再判定を促すこと

### US-6: 宗教・信条上の食事制限への対応

**ストーリー**: ハラールまたはベジタリアンを実践する旅行者として、料理名に現れない食材を避けるために、豚由来成分・アルコール・動物性だしの含有可能性を確認できる。

**受け入れ基準**:
- [ ] AC-6.1: WHEN ハラールを選択したユーザーが判定を実行した THEN システムは豚肉・豚由来成分(ラード、豚骨だし、ゼラチン)・アルコール(みりん、料理酒)の含有可能性を個別に表示すること
- [ ] AC-6.2: WHEN ベジタリアン/ヴィーガンを選択したユーザーが判定を実行した THEN システムは動物性だし(かつおだし、煮干し、豚骨)を含有可能性として表示すること
- [ ] AC-6.3: システムは宗教上の適合性を認証・保証する表現を用いず、あくまで含有可能性の提示に留めること

## 4. 機能要件(Functional Requirements)

### FR-1: 撮影・文字認識

| ID | 要件 | 優先度 | 関連US |
|----|------|--------|--------|
| FR-1.1 | WHEN ユーザーが撮影を実行した THEN システムは端末内OCRによりメニュー画像から文字列を抽出すること | Must | US-1 |
| FR-1.2 | システムはOCRの認識言語ヒントを日本語に固定し、繁体字と日本語漢字の誤認識を抑制すること | Must | US-1 |
| FR-1.3 | システムは抽出した文字列から、価格・住所・店名等を除外し料理名候補のみを抽出すること | Must | US-1 |
| FR-1.4 | IF 画像が暗い・ブレている・傾いている場合 THEN システムは撮影前にガイドを表示し再撮影を促すこと | Should | US-1 |
| FR-1.5 | システムは端末のギャラリーから既存画像を選択して判定できること | Could | US-1 |
| FR-1.6 | システムは撮影画像を端末外へ送信しないこと(未知料理の推論時も、送信するのは料理名テキストのみとする) | Must | US-1 |

### FR-2: 料理特定・アレルゲン判定

| ID | 要件 | 優先度 | 関連US |
|----|------|--------|--------|
| FR-2.1 | システムは料理名候補を正規化(全角半角・送り仮名・カタカナ表記ゆれ・異体字)したうえでローカルDBと照合すること | Must | US-1 |
| FR-2.2 | WHEN 照合が成立した THEN システムはDBの食材IDからアレルゲンを決定論的に導出し、AI推論を行わないこと | Must | US-1 |
| FR-2.3 | システムは料理に紐づく隠れ食材(だし・油脂・調味料)を判定対象に必ず含めること | Must | US-1, US-6 |
| FR-2.4 | IF 照合が成立せず、かつオンラインである THEN システムはAI推論を実行し、結果に「AI推定・未検証」のラベルを付与すること | Must | US-1 |
| FR-2.5 | IF 照合が成立せず、かつオフラインである THEN システムは「判定不可」を表示し、推測を行わないこと | Must | US-5 |
| FR-2.6 | IF AI推論の確信度が閾値未満である THEN システムは結果を表示せず「判定不可」に倒すこと | Must | US-1 |
| FR-2.7 | システムは同一料理名に複数の解釈が存在する場合、最もアレルゲンを多く含む解釈を採用すること(安全側フォールバック) | Must | US-1 |
| FR-2.8 | システムは判定結果を「含有の可能性が高い」「収録データ上は該当なし」「判定不可」の三値で表現し、二値化しないこと | Must | US-1 |

> **Issue #10 決定(2026-08-16, K01)**: FR-2.7は、ローカルDBが複数の解決済み候補を列挙でき、その中から選択できる場合にのみ適用する。候補を一意に解決できない(`unknown`)場合は、`technology-selection.md` §10.3の「判定不可」を優先する。曖昧な候補について安全側に「最もアレルゲンを多く含む解釈」を推測で採用することはしない。詳細は`ui-design.md`「上位仕様差分と決定」を参照。

## 5. 非機能要件(Non-Functional Requirements)

### 5.1 パフォーマンス
- **NFR-1.1**: 収録済み料理の判定は、撮影完了から結果表示まで3秒以内(オフライン、ミドルレンジ端末基準)
- **NFR-1.2**: OCR処理は1画像あたり1.5秒以内
- **NFR-1.3**: AI推論を伴う未知料理の判定は10秒以内。超過時はタイムアウトし「判定不可」を表示
- **NFR-1.4**: アプリのインストールサイズは同梱DBを含めて100MB以内。うち料理DBは20MB以内を目安とする

### 5.2 セキュリティ・プライバシー
- **NFR-2.1**: アレルギー情報は個人情報保護法上の要配慮個人情報に該当し得るため、端末内にのみ保存し、サーバーへ送信・保存しない
- **NFR-2.2**: アカウント登録を要求しない。個人を識別する情報を一切取得しない
- **NFR-2.3**: AI推論API呼び出し時に送信するのは料理名テキストのみとし、撮影画像・プロファイル・端末識別子を送信しない
- **NFR-2.4**: 端末内のプロファイルはOS標準の暗号化ストレージ(Keychain / EncryptedSharedPreferences)に保存する
- **NFR-2.5**: 外部AI APIの利用にあたり、送信データが学習に利用されない設定またはプランを選択する

### 5.3 可用性・信頼性
- **NFR-3.1**: コア機能(OCR・DB照合・判定・確認カード)はサーバー稼働状況に依存せず動作すること
- **NFR-3.2**: IF AI APIが障害または予算上限に達した場合 THEN システムはコア機能を維持したまま、未知料理のみ「判定不可」として縮退動作すること
- **NFR-3.3**: 判定ロジックの変更時は、既知の偽陰性ケースを含む回帰テストセットを全件通過すること

### 5.4 ユーザビリティ・アクセシビリティ
- **NFR-4.1**: 主要導線(起動→撮影→判定→確認カード)を5タップ以内で完結させること
- **NFR-4.2**: 警告表示は色覚多様性に配慮し、色・アイコン・テキストの3要素で冗長化すること
- **NFR-4.3**: OS のフォントサイズ設定(最大設定時)でレイアウトが破綻しないこと
- **NFR-4.4**: 屋外・薄暗い店内の双方で判読可能なコントラスト比(WCAG AA相当)を確保すること
- **NFR-4.5**: 免責・注意文は初回起動時に明示的な同意を取得し、以降も判定画面上に常時表示すること

### 5.5 保守性・拡張性
- **NFR-5.1**: 料理データは `dish_id + 多言語ラベル配列 + 食材ID配列` の正規化構造とし、特定言語に依存しないこと(将来の双方向対応の前提)
- **NFR-5.2**: 食材とアレルゲンの対応は、料理データと独立したマスタとして管理し、アレルゲン基準の追加(EU14品目等)をデータ変更のみで吸収できること
- **NFR-5.3**: 表示言語の追加が、翻訳リソースの追加のみで完結すること
- **NFR-5.4**: AI推論部分をインターフェースで抽象化し、プロバイダ変更をロジック変更なしで行えること
- **NFR-5.5**: 料理データはコードから分離し、非エンジニアでも編集可能な形式(CSV/YAML)でソース管理すること

## 6. 制約条件(Constraints)

### 6.1 プロダクトの位置づけ(最重要)
- **C-1**: 本プロダクトは**注文前に店員へ確認するための補助ツール**であり、摂食の安全を保証しない。医療機器ではなく、医学的助言を提供しない
- **C-2**: 判定は「含まれない」ことの証明を行わない。表示は常に「含有の可能性」または「収録データ上は該当なし」という限定的表現に留める
- **C-3**: 免責事項への同意を初回起動の必須要件とし、アプリストア掲載文にも位置づけを明記する

### 6.2 技術
- **C-4**: クロスプラットフォームフレームワークとして Flutter を採用する(個人開発における保守性と、OCR・ローカルDB系プラグインの成熟度による)
- **C-5**: OCR は端末内で完結する OS 提供機能(iOS: Vision Framework / Android: ML Kit)を用い、通信とコストを発生させない
- **C-6**: アレルゲン判定にローカルLLMを用いない。判定は決定論的なDB照合とし、生成モデルは未知料理のオンライン推論と翻訳に限定する
- **C-7**: ローカルDBは SQLite(全文検索インデックス付き)とする

### 6.3 事業・運営
- **C-8**: ユーザーに対して完全無料で提供する。収益化・広告を行わない
- **C-9**: AI推論APIの費用は開発者が自己負担するため、月次予算上限を設定し、上限到達時は NFR-3.2 の縮退動作に移行する
- **C-10**: 個人開発のため、24時間の障害対応・問い合わせ対応は行わない

### 6.4 法令・データ
- **C-11**: 個人情報保護法における要配慮個人情報の取扱いに準拠する(本設計では端末内保存によりサーバー側の取得を回避する)
- **C-12**: 料理データの構築において、他社サービスのデータベースを無断で複製しない
- **C-13**: ハラール等の宗教的適合性について、認証機関に代わる保証・認定を行わない

- **D-4**: Flutter の主要プラグイン(camera, google_mlkit_text_recognition, sqflite)の保守継続

## 付録A: データモデル方針(design.md への申し送り)

将来の双方向対応(NFR-5.1)を成立させるため、以下の分離を初期から徹底する。この構造を後から変更するのが最も高コストな手戻りとなる。

```
dishes           : dish_id, region, 代表画像
dish_labels      : dish_id, lang(ja/en/zh-Hant/zh-Hans/ko), name, 表記ゆれ配列
dish_ingredients : dish_id, ingredient_id, 確度(確実/一般的/店舗による), 隠れ食材フラグ
ingredients      : ingredient_id, 多言語名
ingredient_tags  : ingredient_id, tag_id  ← アレルゲン/食事制限を同一機構で表現
tags             : tag_id, 種別(JP28 / EU14 / halal / vegetarian / vegan), 多言語名
```

要点は3つ。

1. **料理名を主キーにしない**。`dish_id` を主キーとし、日本語名は多言語ラベルの一つに過ぎない扱いにする。これにより逆方向対応時にスキーマ変更が不要になる。
2. **アレルゲンと食事制限を別テーブルにしない**。どちらも「食材に付与されるタグ」として統一的に扱うことで、EU14品目やその他の基準の追加がデータ投入のみで完結する。
3. **確度を食材レベルで持つ**。「店舗による」食材が1つでもあれば、料理全体の判定は自動的に「要確認」へ降格させる。これが偽陰性0%(KPI-1)を構造的に担保する仕組みとなる。
